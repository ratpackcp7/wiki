# A Field Guide to Sandboxes for AI

This guide explores the technical landscape of executing untrusted code generated or requested by AI agents. As agents move from text generation to action (running programs, installing packages, executing tool calls), the security boundary becomes the most critical part of the infrastructure.

---

## 1. The Core Problem: "Let me run a program"
AI agents recreate the classic malware analysis problem: running hostile code on a machine you care about.
*   **The Threat:** Code generated by models, pasted by users, or pulled from sketchy dependency chains.
*   **Failure Modes:**
    *   **Kernel Exploits:** Escaping to the host machine.
    *   **Exfiltration:** Stealing SSH keys, cloud credentials, or private code.
    *   **Lateral Movement:** Pivoting into internal networks.
    *   **Resource Abuse:** Crypto mining, fork bombs, or runaway builds.

---

## 2. The Three-Question Model for Evaluation
To understand any sandbox, you must answer these three questions:

1.  **What is shared?** (The Boundary: Where is the line drawn between the code and the host?)
2.  **What can the code touch?** (The Policy: Files, network, devices, and syscalls.)
3.  **What survives?** (The Lifecycle: Fresh runs vs. persistent workspaces vs. snapshots.)

### Key Vocabulary
*   **Container:** Process isolation on a shared kernel.
*   **MicroVM:** Minimal VM optimized for fast boot and small footprint.
*   **Runtime Sandbox:** Isolation enforced by a runtime (Wasm, V8) rather than the OS.

---

## 3. Comparison of Sandbox Boundaries

| Type | Mechanism | Host Kernel Exposure | Best For |
| :--- | :--- | :--- | :--- |
| **Container** | Namespaces/Cgroups | **High:** Shares host kernel; all syscalls land on host. | Trusted/Internal workloads. |
| **gVisor** | Userspace Kernel | **Medium:** Interposes a "Sentry" to handle syscalls. | K8s environments needing better isolation. |
| **MicroVM** | Hardware Virt | **Low:** Guest kernel sits behind KVM/Hypervisor. | Multi-tenant SaaS, hostile code. |
| **Wasm/Isolates** | Runtime Constraints | **None:** No syscall ABI; only explicit host imports. | Stateless tool calling, plugins. |

---

## 4. Deep Dive: Linux Building Blocks & Containers
Containers are a "policy sandwich" of four primitives:
1.  **Namespaces:** Isolated views of PIDs, Mounts, Network, and Users.
2.  **Capabilities:** Fine-grained privileges (e.g., `CAP_SYS_ADMIN` is "the new root").
3.  **Cgroups:** Resource limits (CPU, Memory, I/O).
4.  **Seccomp:** Syscall filtering via BPF programs.

> **Critical Insight:** "A tight seccomp profile in a weak boundary is still a weak sandbox... The syscalls you *do* allow still execute in the host kernel."

### Common Container Escapes
*   **`--privileged` mode:** Removes almost all guardrails.
*   **Docker Socket:** Mounting `/var/run/docker.sock` is effectively host root access.
*   **Kernel Bugs:** Vulnerabilities like **Dirty COW** or **Dirty Pipe** allow escalation because the kernel is shared.

---

## 5. Stronger Boundaries: gVisor and MicroVMs

### gVisor (Syscall Interposition)
Uses a userspace kernel (Sentry) written in Go.
*   **The Win:** Reduces host exposure to ~50-70 syscalls.
*   **The Tradeoff:** Performance overhead on syscall-heavy tasks and potential compatibility issues.

### MicroVMs (Hardware Isolation)
The industry standard for "running arbitrary code for strangers."
*   **Firecracker (AWS):** Minimalist, Rust-based, optimized for density. Whitelists only ~24 syscalls and ~30 ioctls for the VMM.
*   **Cloud-hypervisor:** Supports GPU passthrough (VFIO) and Windows guests.
*   **Snapshot/Restore:** Allows "pre-warming" an agent with heavy dependencies and cloning it in milliseconds.

---

## 6. Runtime Sandboxes (Wasm & Isolates)
These flip the model: the code has **no ambient authority**. It cannot see a clock, a file, or a network unless explicitly granted.

### WebAssembly (Wasm)
*   **Capability-oriented:** Uses "preopened directories" to grant access to specific subtrees only.
*   **Example Policy (Pseudocode):**
    ```javascript
    // Give the module a view of ./workspace, not the host filesystem.
    wasi.preopenDir("./workspace", "/work");

    // Allow outbound HTTPS to a specific host.
    wasi.allowNet(["api.github.com:443"]);
    ```
*   **Use Case:** Ideal for "Tool Calling" where an agent needs to run a specific function (e.g., "format this code") without a full OS.

---

## 7. Actionable Decision Matrix

| Workload | Recommended Boundary | Why? |
| :--- | :--- | :--- |
| **Multi-tenant SaaS Agent** | **MicroVM** | Full Linux compatibility + hardware isolation. |
| **RL Rollouts** | **MicroVM** | Needs fast reset via snapshot/restore. |
| **Stateless Snippets** | **gVisor / Wasm** | Low overhead, scoped capabilities. |
| **Tool Calling / Plugins** | **Wasm / Isolates** | Explicit, narrow import surface. |
| **Local CLI Agents** | **OS Sandboxes** | Landlock (Linux) or Seatbelt (macOS) for local dev.
